## 首要嫌疑：帧缓冲被映射成**可缓存**，MMIO 写没有及时落到设备

`paging.cpp` 里帧缓冲走的是 4MB PSE 页：

```cpp
void PagingManager::map_user_4mb(u32 virt_addr, u32 phys_addr) {
    page_dir_virt_[virt_addr >> 22] = (phys_addr & 0xFFC00000)
        | PAGE_PRESENT | PAGE_RW | PAGE_USER | PAGE_PSE;   /* 没有 PCD / PWT */
}
```

**PDE 里没有置 PCD(bit 4)/PWT(bit 3) ⇒ 这段 MMIO 被当成 write-back 可缓存内存。**
x86 上 CPU cache 与 **MMIO 设备不保持一致**：写回缓存的一批像素可能长时间不落到
显存，SVGA 设备读到的就是旧内容 —— 表现正是"**部分像素没写上 / 旧像素没被覆盖**"，
即 I1 的拖影与 I2/I3/I4 的"整个元素不见了"（文字/按钮/菜单都是小块位图，最容易被
"没落盘"吃掉）。

**为什么 QEMU 上看不出来**：QEMU 是软件模拟，显存是宿主内存里的一块数组，
写入在缓存行被逐出的时机上更容易"碰巧"可见；VMware 的 SVGA 有自己的一块 VRAM，
对 MMIO 写序更敏感。**这一点必须在 QEMU 上做隔离验证**（见下）。

**修复方向（待验证）**：给帧缓冲的 PDE 加 **PCD=1（UC，强不可缓存）**，
或 PWT=1 / PAT 走 **WC（写合并，性能更好但需要 PAT 支持）**。
定位点：`src/kernel/paging.cpp` 的 `map_kernel_4mb()` / `map_user_4mb()`，
或给它们加一个 `uncached` 参数，只对帧缓冲生效。

## 次要嫌疑：Ring0 兼容模式自身的差异

Ring0 模式下桌面跑在 CPL0、`int 0x80` 不切栈（内核 C 代码跑在程序栈上）。
虽然 `LS/CAT/CREATE` 这类功能正常，但**图形路径没有在 QEMU 的 ring0 模式下
逐一比对过**。需要和上面的嫌疑分开验证。

## 下一步第一件事：在 QEMU 里做隔离实验

跑同一份 **ring0 模式** 镜像（`g_ring0_mode = true`）并截图对比：

| QEMU(ring0) 的结果 | 结论 |
|---|---|
| **也缺**标题栏文字/图标文字/菜单 | 是 **ring0 模式或内核侧**的问题（与 VMware 无关），从渲染路径查 |
| **一切正常**，只有 VMware 缺 | 是 **VMware + LFB 缓存**问题 → 按上面的 PCD/WC 修 |

## 备注

- "三大金刚键" = 最小化 / 最大化 / 关闭。
- 这些问题**不影响**内核、shell、文件系统功能，只影响窗口系统的渲染完整性。
- `RUN` 不可用是 Ring0 兼容模式的**结构性限制**（CPL0 下 `iretd` 不弹 SS/ESP，
  任务切换无法恢复目标任务的应用栈），不是渲染问题，单独记录。
