## 状态：**4 项全部定位并修复**（同日）

**根因不在 VMware，而在 Ring0 兼容模式自身的一个补丁错误。**

### 定位过程（隔离实验）

1. **先在 QEMU 里跑同一份 ring0 模式镜像并截图** —— I3（图标文字缺失）**同样复现**，
   说明与 VMware 的 LFB 缓存无关（原"MMIO 被缓存"的猜想被排除）。
2. **再跑 ring3 模式截图对照** —— ring3 下 7 个图标名全部正常渲染。
   ⇒ 差异由 ring0 模式引入。
3. **在内核 `IOCTL_TEXT_UTF8` 里打印收到的 x/y/color/text**，两种模式对比：

   | 文本 | ring3 | ring0（修复前） |
   |---|---|---|
   | 图标名「文件」 | `x=0x3C`(60) ✅ | **`x=0xFFFFF994`(-1644)** ❌ |
   | 提示文字 | `x=0x10` ✅ | `x=0x10` ✅ |

   图标名的 x 变成负数 → 被裁剪到屏幕外 → 整块消失。

### 根因

`src/kernel/isr.cpp` 里我为 ring0 兼容模式加的这段"补 user_esp"：

```cpp
if (g_ring0_mode && !from_user) { r->user_esp = r->_esp; r->user_ss = 0x10; }
```

**同级（CPL0→CPL0）中断帧只有 13 个字**（`edi..eax, vec, err, eip, cs, eflags`），
**根本没有 `user_esp/user_ss` 这两个槽位**。`user_esp` 的偏移是 52，而帧起点 `r`
满足 `r + 52 = 中断发生时的 ESP` —— 那正好是**程序当前栈帧最底部**，
也就是 `text_cn()` 正在构造的 ioctl 结构体的头 8 字节（`p.x, p.y, p.c`）。

于是**每次 syscall 都把程序正要传给内核的结构体前 8 字节踩坏** → 内核收到
垃圾坐标 → 文字画到屏幕外。

这解释了全部症状：

| 现象 | 解释 |
|---|---|
| I3 图标名不显示 | `p.x` 被改成负数 → 画到屏幕外 |
| I2 窗口标题栏文字/三大金刚键不显示 | 同一机制（标题栏文字与按钮都走 `text()/text_cn()`） |
| I4 右键菜单不弹出 | 同一机制，菜单项文字被画到屏幕外（看起来像"没弹"） |
| I1 拖动窗口有拖影 | 同一机制，拖动重绘用的 fill/rect 结构体坐标被踩坏，旧位置没被正确清除 |
| （冒烟里的）`CAT` 输出乱码 / 文件内容校验失败 | 同一机制，输出用的小结构体也被踩 |

### 修复

**删掉那段补丁**（`isr.cpp`）。同级帧本来就没有那两个槽位，而真正的消费方
（`sys_fork` / `schedule` / `task_check_signals`）都已按 `(r->cs & 3)` 自行分支处理。
并在该处留了醒目注释，避免以后有人再"补"一次。

### 验证（QEMU）

- ring0 模式重新截图：**7 个图标名全部渲染出来**，且与 ring3 基准的像素统计
  逐项一致（`y=64-127: (0,0,170) 29101 / (255,255,255) 1191` 完全相同）。
- 冒烟回归：`OK: 文件内容正确` 由 FAIL 变 OK；**剩下失败的只有 `RUN` 系列**，
  那正是 Ring0 兼容模式的设计限制。

**⇒ 结论：这不是 VMware 问题，与本仓的 LFB 缓存猜测无关。**

## 备注

- "三大金刚键" = 最小化 / 最大化 / 关闭。
- 这些问题**不影响**内核、shell、文件系统功能，只影响窗口系统的渲染完整性。
- `RUN` 不可用是 Ring0 兼容模式的**结构性限制**（CPL0 下 `iretd` 不弹 SS/ESP，
  任务切换无法恢复目标任务的应用栈），不是渲染问题，单独记录。
