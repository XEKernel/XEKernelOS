## 2. 详细分析

### #1 构建阻断：`syscall4` 实参个数不匹配（P0）

上一次提交 `0a2d6a7`（LFN 读侧支持）**本身编译不过**——即该提交从未通过完整构建。

```
src/user/lfstest.cpp:29:5: error: no matching function for call to 'syscall4'
   29 |     syscall4(SYS_WRITE, (int)line, lp);
src/user/usys.h:57:19: note: candidate function not viable:
      requires 4 arguments, but 3 were provided
```

**根因**：`usys.h` 里 `syscall4(num, a1, a2, a3)` 是唯一的底层入口（`ecx`/`edx` 传参），
`SYS_WRITE` 的 ABI 是 `ebx=str, ecx=len`（见 `syscall.cpp:42` `sys_write()`），
所以第 3 个寄存器位必须显式补 0。`lfstest.cpp` 漏写。

**修复**：补第三个实参 `0`，与同文件其它调用（`syscall4(SYS_VFS_LIST, ...)`、
`syscall4(SYS_FREAD, fd, (int)buf, 500)`）保持一致。

```diff
-    syscall4(SYS_WRITE, (int)line, lp);
+    syscall4(SYS_WRITE, (int)line, lp, 0);
```

**影响面**：`make` 在 `build/lfstest.elf` 处中止，`build/disk.img` 不生成
（`all` 的后续依赖全部跳过），因此**连磁盘镜像都拿不到**，VMware 侧无从谈起。

### #2 VFS 接口缺口：`RamDisk` 未实现结构化目录列表（P2）

**唯一线索**是编译器告警，未被处理：

```
src/fs/ramdisk.h:37:10: warning: 'RamDisk::list' hides overloaded virtual
      function [-Woverloaded-virtual]
src/fs/vfs.h:53:17: note: hidden overloaded virtual function
      'Filesystem::list' declared here: different number of parameters (3 vs 2)
```

**根因**：`Filesystem` 有虚函数 `list(const char*, DirEntry*, u32)`，默认实现直接
`return -1`（「默认不支持」）。`FatFilesystem` 正确 `override` 了它，
**`RamDisk` 没有** —— 它只有一个不同签名的 2 参 legacy `list(char*, u32)`。
于是 `vfs.cpp:148` 的 `fs->list(rel, entries, max)` 对 `/tmp` 落到基类默认实现：

```cpp
int vfs_list_dir(const char *path, DirEntry *entries, u32 max) {
    ...
    return fs->list(rel, entries, max);   // RamDisk → Filesystem::list → -1
}
```

**影响**：任何经 VFS 列举 `/tmp` 的调用（`SYS_VFS_LIST("/tmp")`、未来的资源管理器
侧栏）恒失败。当前 GUI 与 shell 的 `/tmp` 走的是 legacy 路径（`rd_list` →
`RamDisk::dir/list` 2 参版），所以**尚未暴露**，属潜在缺陷。

**修复**：新增 `int list(const char *path, DirEntry *e, u32 max) override;`，
按槽位输出在用文件（平铺 FS，`path` 忽略），名字拷贝限长 31 字节并补 NUL。
同时消除 `-Woverloaded-virtual`（派生类内同名重载后不再隐藏基类虚函数）。

### #3 物理页分配器上界算错（P3，潜在越界分配）

```cpp
total_pages = (mem_top - bm_start) / PAGE_SIZE;   // ← 从位图起点起算
u32 bm_bytes = (total_pages + 7) / 8;
u32 bm_pages = (bm_bytes + PAGE_SIZE - 1) / PAGE_SIZE;
bitmap     = (u8 *)bm_start;
first_page = bm_start + bm_pages * PAGE_SIZE;     // ← 可分配页却从位图之后起算
```

`mm_alloc_page()` 的循环上界用 `total_pages`，返回 `first_page + i * PAGE_SIZE`：
两者起点不同，尾部 `bm_pages` 次分配会返回**内存上界（`mem_top`）之外的物理地址**。
`mm_free_page` 的界内判断亦同源偏移。

实际未触发只因可分配页远多于用量（64MB 位图仅 1 页，越界窗口 = 1 页，永远用不到），
属被掩盖的缺陷。**已在内存充足的机器上验证无回归**。

**修复**：`first_page` 定下后把位图页从可分配页数里扣除，并让 `free_count` 与之同源：

```cpp
total_pages = (total_pages > bm_pages) ? (total_pages - bm_pages) : 0;
free_count  = total_pages;   // mm_reserve() 随后继续扣减预留区
```

## 6. 追加发现（同日 VMware 实测后）

### #5 死代码掩盖了关键证据（P2，未改代码，已更正文档）

VMware 上 triple fault 的排查记录（`docs/VMWARE.md` §5.1）里，有一条结论性证据：

> 「进 ring3 时关闭中断（IF=0）→ ❌ 仍然 triple fault → **与中断投递无关**」

**这条证据无效。** 该实验改的是 `src/kernel/task.cpp:219 task_start_user()`，
而全工程 grep 的结果是：

```
src/kernel/task.cpp:219:void task_start_user(void) {     ← 只有定义，没有任何调用点
```

`task.h:114-115` 另外声明了 `task_start_user()` / `task_launch_user()`，
后者**连定义都没有**。真正的 ring3 入口是 `user.cpp: enter_user_mode()`（由
`loader.cpp` 调用），这条死代码从未被执行过。

**影响**：那次「IF=0」测试等于编译了一份没人调用的函数然后运行原路径，
**中断因素因此并未被排除**——而「PIT 在 iret 之后立刻投递」正是当前最需要验证的方向之一。
已在 `VMWARE.md` 该行标注作废并说明原因。

**建议**：要么删掉 `task_start_user()` / `task_launch_user()` 这两个死符号，
要么把它们修成可用（帧格式对齐 `registers_t`）并让测试真正走那条路径。
本次未改动，避免在被测状态不清的情况下扩大改动面。
